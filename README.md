# Дневник питания и активностей

Telegram-бот на aiogram 3 + локальная LLM (Ollama/LM Studio) + SQLite + веб-дашборд на FastAPI.

## Структура

```
nutrition_bot/
├── run_all.py          # ЕДИНЫЙ ЗАПУСК: бот + дашборд в одном процессе
├── accounts.py         # CLI управления аккаунтами дашборда
├── auth.py             # пароли (PBKDF2) и сессионные куки (HMAC)
├── net.py              # системный DNS-резолвер вместо aiodns
├── bot.py              # aiogram 3: FSM-опрос по КБЖУ + сохранение свободных заметок
├── database.py         # async SQLite (aiosqlite), схема и запросы
├── llm_client.py       # OpenAI-совместимый клиент к Ollama / LM Studio
├── config.py           # конфиг из .env, пути через pathlib
├── web/
│   ├── app.py          # FastAPI-дашборд на той же базе
│   └── templates/      # index.html (дни), day.html (карточка дня)
├── requirements.txt
└── .env.example
```

## Установка

```bash
python -m pip install -r nutrition_bot/requirements.txt
```

Скопировать `.env.example` → `nutrition_bot/.env` и указать `BOT_TOKEN`.

## Локальная модель

```bash
ollama pull qwen2.5:7b-instruct
ollama serve
```

Для LM Studio достаточно поменять `LLM_BASE_URL` на `http://localhost:1234/v1` —
код использует один и тот же OpenAI-совместимый эндпоинт `/chat/completions`.

### Почему Qwen2.5-7B, а не 14B

| | Qwen2.5-7B-Instruct | Qwen2.5-14B-Instruct |
|---|---|---|
| VRAM / RAM (Q4_K_M) | ~5 ГБ | ~9–10 ГБ |
| Скорость (типовой ноутбук/GPU средний) | ~35–60 tok/s | ~15–25 tok/s |
| Латентность ответа бота | ~1–2 с | ~3–6 с |
| Качество на коротком JSON-парсинге | достаточно | чуть выше |

Задачи здесь узкие: классификация короткой русской фразы в одну из шести
категорий с выдачей JSON и генерация сводки из уже посчитанных цифр. Это
задачи, где 7B практически не уступает 14B — арифметику модель не выполняет
(суммы считает SQL), а рассуждений в несколько шагов не требуется. При этом
бот отвечает в диалоге: латентность важнее, а 14B даёт 3–6 секунд задержки на
каждое сообщение и не влезает в 8 ГБ VRAM.

Итог: по умолчанию **Qwen2.5-7B-Instruct**.

### Замеры точности оценки блюд

Проверено на 8 блюдах, по 3 прогона на каждое, сверка с диапазонами из
справочников. «Попадание» — оценка внутри правдоподобного диапазона.

| вариант | попаданий | медианная ошибка | время |
|---|---|---|---|
| 7b, развёрнутый промпт с ориентирами ккал/100 г | 29% | — | 5.2 с |
| 7b, короткая инструкция | 46% | 23% | 3.1 с |
| **7b, короткая инструкция + примеры (используется)** | **58%** | **20%** | 5.5 с |
| 7b, разложение на ингредиенты | 33% | — | 45 с |
| qwen3:14b | 67% | — | 190 с |

Два вывода, которые стоит знать при доработке промпта:

1. **Развёрнутые инструкции сделали хуже.** Список «ориентиров калорийности на
   100 г» уронил точность вдвое против короткой инструкции — модель их
   игнорировала и завышала (карбонара 350 г → 1275 ккал при норме 600–900).
   Три примера-эталона в диалоге работают лучше любых правил.
2. **Разложение на ингредиенты не помогло.** Звучит логично, но 7b ошибается
   и в весах, и в справочных значениях, а ошибки складываются — плюс 45 секунд
   ожидания вместо 5.

qwen3:14b точнее всех, но это модель с режимом рассуждений: 190 секунд на
блюдо, для чата непригодно. Если оценки нужны точнее — смотри в сторону
qwen2.5:14b-instruct (без рассуждений) или подключай справочник CalorieNinjas /
USDA вместо модели.

**Оценки остаются приблизительными.** Медианная ошибка ~20%, отдельные блюда
мимо вдвое. Записи от модели помечены в дашборде значком «≈ оценка», чтобы их
было видно среди точных. Когда цифры важны — вводи их вручную числами.

Если модель не запущена, бот продолжает работать: классификация заметок
падает на резервную эвристику по ключевым словам (`_fallback_note_insight`),
сводка дня выводится обычным текстом.

## Запуск

Всё сразу (бот + дашборд в одном процессе) — рекомендуемый способ:

```bash
python -m nutrition_bot.run_all
```

Ctrl+C останавливает обе части. Если падает одна — вторая гасится следом,
чтобы не оставалось «полуживого» процесса.

Или по отдельности, если нужно перезапускать их независимо.

Бот:

```bash
python -m nutrition_bot.bot
```

Дашборд (в отдельном терминале):

```bash
python -m nutrition_bot.web.app
```

Дашборд: http://127.0.0.1:8000 — таблица по дням, клик по дате открывает
карточку с калориями, БЖУ, заметками и всеми сообщениями за день.

## Аккаунты дашборда

Вход по логину и паролю. **Логин — это твой @username из Telegram** (без
собачки, регистр не важен): по нему аккаунт связывается с записями в дневнике.

Создать главный аккаунт (видит данные всех):

```bash
python -m nutrition_bot.accounts add @твой_username --admin
```

Обычный аккаунт — видит только свои дни:

```bash
python -m nutrition_bot.accounts add @друг
```

Пароль запрашивается скрытым вводом и в базу попадает только PBKDF2-хэшем
(240 000 итераций, случайная соль). Остальные команды:

| команда | что делает |
|---|---|
| `accounts list` | список аккаунтов и их привязка к Telegram |
| `accounts passwd @user` | сменить пароль |
| `accounts role @user admin` | выдать или отобрать права главного |
| `accounts delete @user` | удалить аккаунт (данные дневника не трогает) |

Как устроен доступ:

* **admin** видит все дни и может переключаться между пользователями в шапке.
* **user** видит только свои записи. Подстановка чужого `?user_id=` в адресную
  строку игнорируется — фильтр всегда принудительно заменяется на собственный id.
* Гость без сессии на любую страницу получает редирект на `/login`.

Сессия — подписанная HMAC кука (`httponly`, `samesite=lax`, срок 14 дней).
Ключ подписи создаётся автоматически в `data/session.key` с правами `0600`;
удалить файл = разлогинить всех.

Если аккаунт создан раньше, чем человек впервые написал боту, привязка
произойдёт автоматически при первом же его сообщении — по совпадению @username.

Дашборд слушает только `127.0.0.1`, то есть снаружи недоступен. Если
понадобится открыть его в сеть — сначала поставь HTTPS-прокси и выставь
`WEB_HTTPS=true`, чтобы кука сессии передавалась только по HTTPS.

## Логика диалога

* Любое сообщение → сохраняется в `messages` и в `notes` с категорией от LLM,
  без дополнительных вопросов.
* Сообщение со словом «калории» / «ккал» / «еда» / «бжу» → бот спрашивает
  «Что ел?» и понимает три вида ответа:
  * **описание блюда** — «паста карбонара 350 г», «2 сырника»: КБЖУ оценивает
    локальная модель, запись помечается как оценка;
  * **строка чисел** — «530 32 14 60» (ккал, Б, Ж, У): записывается сразу;
  * **одно число** — пошаговый опрос, как раньше (ккал → белки → жиры → углеводы).
* `/today` — сводка за сегодня, `/cancel` — прервать опрос.

## Дневные цели по КБЖУ

Задать цель одной строкой (ккал, белки, жиры, углеводы):

```
/goal 2000 150 60 200
```

Или просто `/goal` — бот спросит четыре значения по одному, как при вводе еды.
`/goal сброс` удаляет цель.

После этого каждый итог дня показывается с прогрессом и остатком:

```
• Калории: 2500 / 2200 ккал  ██████████ 114%  (перебор на 300)
• Жиры: 20.0 / 70.0 г  ███░░░░░░░ 29%  (осталось 50.0)
```

На дашборде в карточке дня появляются полоски прогресса (перебор красным),
а в таблице дней — колонка «% цели». Если цель не задана, всё работает
по-прежнему, просто без прогресса. Цель хранится в таблице `goals`, по одной
на пользователя, и применяется ко всем дням — история прошлых целей не ведётся.

## Схема БД

| таблица | назначение |
|---|---|
| `users` | пользователи Telegram |
| `messages` | все входящие сообщения (`kind`: `note` / `meal_trigger`) |
| `notes` | свободные заметки с категорией и краткой сутью от LLM |
| `meals` | ккал/Б/Ж/У с датой и временем |
| `web_accounts` | логины дашборда: хэш пароля, роль, привязка к Telegram |

Все таблицы содержат `created_at` (ISO-время) и `day` (`YYYY-MM-DD`) для
быстрой агрегации по дням.

## Кроссплатформенность

Пути только через `pathlib`, каталог БД создаётся автоматически,
внешних бинарников кроме самой Ollama/LM Studio не требуется.
